## Фактическая блокировка

Три независимых наблюдения согласуются:

1. cloud environment status: observations_current=true, network policy restricted/enforced, **overpass-api.de отсутствует в effective_allowed_hosts**.
2. Локальный не содержащий секретов `/etc/codex/network-policy.json` тоже не содержит разрешения этого домена. Этот файл только описывает политику, редактирование не предоставляет доступ.
3. Реальный curl через штатный HTTPS proxy:

```text
curl --head --connect-timeout 10 --max-time 20 https://overpass-api.de/api/status
curl: (56) CONNECT tunnel failed, response 403
HTTP/1.1 403 Forbidden
server: envoy
proxy_connect_status=403
http_status=000
```

403 возникает **на запросе CONNECT к облачному proxy Envoy**, до TLS-соединения с целевым сайтом. HTTP-запрос Overpass к целевому серверу не состоялся. `http_status=000` — отсутствие ответа целевого HTTP-сервера, не его код ошибки. Нулевой ssl_verify_result в этом случае не доказывает успешную проверку сертификата: целевой TLS ещё не начался. Нельзя по этим данным утверждать, что Overpass недоступен сам по себе, что виноват его rate limit, Karing, Tailscale, PostgreSQL/SQLite, токен Telegram или синтаксис GIS-запроса.

В сохранённом черновике среды test (revision 4) домен уже присутствует, но **в активном экземпляре разрешения нет**. Черновик настроек и работающий экземпляр — разные состояния. Нельзя считать доступ открытым по одному изменению списка в UI. Счётчики draft revision и runtime spec revision относятся к разным объектам; вывод сделан по фактическому списку и CONNECT, а не сравнению номеров.

## Поддерживаемое продолжение

### Облачная среда

В настройках **именно среды test** проверьте сохранённый network allowlist, сохраните/опубликуйте нужную версию. Затем запустите или привяжите задачу к этой опубликованной версии. Если Publish уже выполнен, текущий экземпляр всё ещё не получил изменения: нужен новый/перезапущенный экземпляр **с опубликованной конфигурацией**, а не перезапуск Node.js внутри прежнего контейнера.

Критерий применения — `overpass-api.de` появился в эффективном списке среды и CONNECT к нему перестал возвращать policy 403. Для реальной карты дополнительно нужны разрешённые tile.openstreetmap.org / *.tile.opentopomap.org. Если после запуска правильной опубликованной версии status по-прежнему не отражает разрешения, это проблема применения конфигурации платформой: обратитесь в поддержку Codex с данным отчётом. Из процесса приложения нельзя исправить egress policy.

После этого повторить `npm run maps:prepare -- --resort dombay`, проверить counters/quality/source IDs, выполнить реальный браузерный тест и сохранить его реальные screenshots. Только затем — четыре следующих контрольных курорта и экспорт пакета.

### Подготовка на другом разрешённом ПК

Если быстро применить cloud policy не удаётся, уже поддерживается независимый путь без обхода ограничений:

1. На ПК с разрешённым доступом установить зависимости через 01_INSTALL.bat.
2. Открыть 09_UPDATE_MAPS.bat → **1** → Домбай; дождаться фактической загрузки и прохождения качества.
3. После успеха → **4**, экспортировать `.slopemap`.
4. Передать файл на Windows-хост → 09_UPDATE_MAPS.bat → **5**: проверить список/источники и установить пакет. Либо приложить пакет к следующему сообщению для проверки/импорта в эту среду.

Файл переносит только карты; пользовательскую БД и конфигурацию не переносит. Инструкции альтернативных OpenSkiData и регионального OSM: [REAL_RESORT_IMPORT_RU.md](REAL_RESORT_IMPORT_RU.md). Наличие адаптеров не означает, что реальные данные уже получены.

Для обхода proxy не отключались HTTP_PROXY/HTTPS_PROXY, не использовались IP-адреса вместо запрещённого домена, сторонние relay, DNS/маршрутные изменения или отключение TLS-проверки.
