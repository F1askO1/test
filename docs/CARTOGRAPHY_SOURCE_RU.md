# Домбай: исходные площади, генерализация и проверка всей подложки

Изменения продолжают `cf27381` в `fix/map-readability` для существующего Draft PR #3. Общая структура интерфейса не переделана. Рабочие SQLite, `.env`, GPS-записи, Telegram, Tailscale и загрузчики не изменялись. Импорт и браузер выполнялись в отдельном `artifacts/cartography/map-data`, API — порт 3099 с SQLite `:memory:`.

## Подтверждённая причина лишних линий

Исследован настоящий предоставленный `resort.osm`, а не восстановленная по картинке схема. Полный исходник сохранён как ODbL-тестовая фикстура [resort.osm](../tests/fixtures/dombay/resort.osm), SHA-256:

`2e03fa6e580865de67aeb06799f9a4c5ac06cecace81e50a111736b13b73d3d0`

В XML 154 ways и 7 relations. **Все семь отношений имеют `type=multipolygon`, `route=piste`, `piste:type=downhill`.** У них 115 вхождений участников, 109 уникальных ways; роль outer у 114 вхождений, inner у одного. Это границы площадей, а не 109 самостоятельных осевых спусков. Старое наследование тегов отношения назначало им `piste:type`/сложность и превращало открытые куски периметра в множество цветных «трасс». Оптимизация только замкнутых ways эту ошибку исправить не могла.

[way 879140376](https://www.openstreetmap.org/way/879140376) явно имеет **`area=yes`, `name=Сулахат`, `piste:difficulty=easy`, `piste:grooming=classic`**. Он сохранён как площадь. [way 469940513](https://www.openstreetmap.org/way/469940513) и [way 469940517](https://www.openstreetmap.org/way/469940517) сами не имеют лыжных тегов; их назначение определяется multipolygon-членством.

## Представление и генерализация

- Исходные lines сохраняются; добавлены `geometryRole` и отдельные `areas`. Старые пакеты читаются, однако без нового импорта нельзя угадать утраченное членство открытых ways в multipolygon.
- Границы подтверждённых площадей не рисуются как отдельные спуски. Сами площади имеют слабую заливку без цветного периметра. Их можно найти по имени или выбрать; карточка явно сообщает о площадной природе и показывает источник/границы.
- Остаются 29 линейных участков и 13 подъёмников: **42 непрерывные цепочки, 644 атомарных ребра**. Это не количество официальных трасс. В предыдущем представлении без исходной семантики было 149 цепочек/1273 ребра.
- Упрощение Douglas–Peucker работает в экранных пикселях: допуск 1,1 px ниже z14, 0,55 px до z16, 0,18 px на близком масштабе. Выход — подмножество исходных вершин, без перемещения координат. Концы, общие узлы/развилки, совместные конфликтующие сегменты и подъёмники защищены. Выделенная линия использует полную геометрию.
- Число вершин линейного представления: 207 на z12, 245 на z13, 468 на z15, 653 на z17; без LOD — 686. Упрощение не передаётся в GPS Engine.
- Выбор пальцем по-прежнему независим от порядка Canvas-панелей; срок жизни рендереров постоянный, гонка `clearRect` не возвращена.

## Подложка: что было неправильно

Старый тест подтверждал лишь `leaflet-tile-loaded > 0`. Этого недостаточно ни для полного окна, ни для нового масштаба. Снимок выбранной трассы делался после открытия карточки, без ожидания новых тайлов: во время анимации старый растр может быть временно растянут. Кроме того, прежняя конфигурация разрешала z19 при `maxNativeZoom=17`, то есть потенциальный overzoom 4×. По одним Windows-скриншотам нельзя однозначно установить HTTP-причину отсутствующих тайлов или точный zoom неудачного кадра; теперь для этого сохраняются измерения.

Новая модель:

1. Считает **только текущий логический tile zoom** и пересечение каждого тайла с реальным прямоугольником карты.
2. Требует завершённого декодирования (`complete`, `naturalWidth >= 256`, loaded-класс). Ошибка/незавершённость не засчитывается.
3. Вычисляет объединение загруженных прямоугольников. Перекрытия и старые zoom-уровни не могут завысить покрытие. Даже если DOM не создал нужный тайл, непокрытая площадь остаётся видимой диагностике.
4. Различает loading, ready (всё видимое окно покрыто), partial и unavailable. Публикует число видимых/загруженных/ошибочных/ожидающих изображений, процент покрытия и непокрытые CSS px². Погрешность границ не более 1 px² / 0,0001%.
5. На resize сверяет кэш размера Leaflet с DOM. При ошибке или истечении 12 секунд повторяет только отсутствующие/ошибочные видимые изображения **один раз** на стабильное окно. Успешные не скачиваются повторно. Для отсутствующих DOM-слотов предусмотрена однократная перепроверка размера и redraw.
6. После неудачного повтора включает резерв OSM; частичный успех больше не блокирует fallback. Циклов между провайдерами нет. Пользователь может явно нажать «Повторить». OSM — обычная карта, а не топографическая замена.

HTTP-код кросс-доменного `<img>` приложению обычно недоступен. Поэтому UI честно сообщает ошибку изображения, а **Playwright сохраняет реальные response status / requestfailed** в `tile-network.json`, без токенов и URL-параметров. Не добавлены двойные fetch-запросы, CORS-прокси или отключение TLS.

### Масштаб, Retina и растр

OpenTopoMap ограничен z17, резерв OSM — z19. Карта не увеличивает рельеф за пределы предоставленного нативного масштаба. На Retina до предела провайдера запрашивается следующий нативный z, изображение 256 px размещается в 128 CSS px. На максимальном z более детальных тайлов у этого источника нет; DPR3 нельзя превратить в настоящий 3× растр искусственной интерполяцией. JSON диагностики содержит requestZ, логический z, naturalWidth, CSS-прямоугольник и число пикселей источника на CSS-пиксель.

В OpenTopoMap уже присутствуют запечённые лыжные/дороговые обозначения. Их нельзя удалить стилем наших векторов. Для полного контроля над картографией уровня Skill потребуется разрешённая топографическая подложка/DEM с подходящей лицензией **без встроенного лыжного слоя** либо собственная генерация рельефа. В OSM/PBF нет необходимой непрерывной модели высот. В этом изменении такой рельеф не выдумывается и непроверенный провайдер не подключается.

## GPS и данные

GPS map matching использует исходные координаты, никогда не LOD-представление. Граница площади не считается осью трассы. Подтверждённая геометрия площадей передаётся тем же `analyze()` через worker и серверное сохранение, чтобы движение внутри известной площади не превращалось в ложный фрирайд. При конфликтующих пересекающихся площадях без уверенного линейного совпадения — unknown; `backcountry` учитывается отдельно. Прежние гистерезис/точность/разрывы и меры против ложной уверенности сохраняются. Схема SQLite не менялась, сохранённые анализы задним числом не переписываются.

## Проверки и границы результата

TypeScript и сборка проходят. **102 модульных теста и 21 браузерный сценарий прошли; 1 strict-тест настоящего рельефа явно пропущен** из-за CONNECT 403. Дополнительный визуальный прогон трёх мобильных размеров также прошёл. Реальные source-тесты сравнивают все координаты с XML, проверяют восемь колец/площадей, protected junctions, zoom-LOD и сохранность исходных объектов. Синтетика используется только в явно обозначенных тестах GPS/holes/conflicts и управляемых тестах доставки изображений.

В облаке по-прежнему enforced restricted policy без tile-хостов. 2026-11-06 штатный HTTPS proxy вернул `CONNECT 403` к `a.tile.opentopomap.org` **до обращения к провайдеру**. Обходов не выполнялось. Поэтому **снимки настоящего рельефа здесь не получены**, strict `dombay-real.spec.ts` явно пропущен в offline-прогоне. ## Применение на Windows и строгая повторная проверка

Обновите код ветки через существующий процесс установки. Новый готовый пакет: [dombay-2026-11-06.slopemap](../map-sources/prepared/dombay-2026-11-06.slopemap), SHA-256 `ac6dee16fe0a20c5a4e7ad4239b5593aa53a7b8cd0532ec4b93db09aa5dcba77`. Он содержит только публичные OSM-данные/семантику площадей, не `.env`/SQLite/GPS. `maps:package inspect` проходит. Установите его существующим меню карт после обновления кода; старый пакет без семантики не исправится одним обновлением CSS.

Для **изолированного** теста в PowerShell:

```powershell
$env:SLOPEMATE_TEST_MAPS = "$PWD\artifacts\dombay-source-check\map-data"
npm run maps:package -- import map-sources/prepared/dombay-2026-11-06.slopemap $env:SLOPEMATE_TEST_MAPS
Remove-Item Env:SLOPEMATE_MAP_OFFLINE -ErrorAction SilentlyContinue
npm run build
npm run test:e2e -- dombay-real.spec.ts
```

Тест требует настоящий OpenTopoMap и полное покрытие после **каждого** изменения камеры. Ждёт окончания zoom и несколько стабильных измерений. Скриншоты делаются `fullPage:false`, чтобы сама процедура не меняла viewport. Он сохраняет `map.png`, `piste.png`, `parallel-before.png`, `parallel-after.png`, `junction.png`, coverage JSON каждого вида и `tile-network.json` даже при ошибке. Частичная карта или обычный OSM вместо рельефа не дают успешного прохождения. Если тест не проходит, сохраните эти диагностические JSON вместе со скриншотами: по ним можно определить конкретные тайлы/HTTP-коды, а не просто увеличить ожидание.

На физическом iPhone остаётся проверить читаемость настоящего растра, safe areas, выбор площадей/осей и реальную запись. Этот PR не объявляет эти ручные проверки пройденными.
