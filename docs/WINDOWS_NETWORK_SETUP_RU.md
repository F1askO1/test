# SlopeMate: запуск на Windows 10, Karing и Cloudflare

Эта инструкция предназначена для Windows 10 x64, Node.js 24 LTS и существующего приложения. Интерфейс, GPS и база не заменены. Launcher не меняет системный DNS, маршруты, настройки Karing или содержимое SQLite.

## Три разных соединения

```text
Телефон / Telegram Mini App
       │ HTTPS
       ▼
Cloudflare → cloudflared → 127.0.0.1:3001 → Express + React + SQLite

Node / grammY → локальный SOCKS Karing → Telegram Bot API
```

Node обслуживает приложение и хранит данные. Бот обращается к Telegram API для команд, меню, ответов и получения обновлений. Cloudflare даёт внешнему телефону HTTPS-доступ к локальному HTTP-серверу. Туннель не исправляет соединение Node → Telegram API, а прокси бота не публикует приложение.

Если прямой TCP 443 к `api.telegram.org` недоступен, бот не сможет зарегистрировать команды или получать сообщения. HTTP-сервер при этом обязан продолжать работать. Теперь его lifecycle независим от бота.

## Сначала настройте Karing

1. Откройте настройки Karing и найдите раздел локального прокси: SOCKS / SOCKS5 / inbound / mixed port (название зависит от версии).
2. Уточните **реальный SOCKS5-порт**, адрес прослушивания и необходимость логина/пароля. HTTP-порт не обязательно поддерживает SOCKS. Пример `7891` не является заданным портом приложения.
3. Оставьте локальный SOCKS-прокси Karing работающим, а глобальный **TUN выключите** для первого теста. При необходимости выключите системный HTTP-прокси Karing штатными настройками клиента, чтобы Cloudflare шёл напрямую. Не закрывайте весь Karing, если он обслуживает нужный SOCKS-порт.
4. Убедитесь, что выбранный маршрут Karing действительно открывает Telegram API. Проверка TCP-порта подтверждает только наличие слушателя, не работу SOCKS и не доступ к Telegram.
5. Не включайте доступ к локальному прокси из LAN без отдельной необходимости. Launcher использует loopback.

В `.env` задайте, например:

```dotenv
TELEGRAM_PROXY_URL=socks5://127.0.0.1:ВАШ_ПОРТ
```

Замените `ВАШ_ПОРТ` числом. Поддерживается и `socks5h://127.0.0.1:ВАШ_ПОРТ` — этот вариант передаёт DNS имени Telegram прокси. У `socks5://` имя разрешается локально. Если DNS подменяется или блокируется, проверьте вариант `socks5h`.

Если SOCKS требует пароль, формат `socks5h://LOGIN:PASSWORD@127.0.0.1:PORT`; специальные символы в логине/пароле должны быть URL-encoded. Значение хранится только в `.env`. Не отправляйте пароль/токен в переписку и не публикуйте файл. Пустой `TELEGRAM_PROXY_URL=` означает прямое соединение.

В облачной среде невозможно узнать ваш порт или поменять настройки установленного на Windows Karing. Нужны только данные о типе локального входа, адресе и порте; секреты заполняйте локально.

## Первый запуск двойным щелчком

Распакуйте/обновите проект, сохранив существующие `.env` и `data/`. Путь с пробелами поддерживается, например `C:\Users\user\SlopeMate\test-main`.

1. Установите официальный Node.js **24 LTS** с npm. После установки откройте новое окно CMD.
2. Установите официальный `cloudflared` для Windows x64. Утилита должна быть в PATH либо укажите полный путь в `.env`:

   ```dotenv
   CLOUDFLARED_PATH=C:\Tools\cloudflared.exe
   ```

   Кавычки вокруг пути не нужны, даже если в нём есть пробелы. Launcher не загружает исполняемые файлы из непроверенных источников.

3. Запустите `01_INSTALL.bat`: он выполнит `npm ci`, создаст `.env` **только если его нет**, соберёт проект. База и существующие настройки сохраняются.
4. Запустите `05_EDIT_ENV.bat` (Блокнот). Введите ваш токен BotFather и настройки:

   ```dotenv
   NODE_ENV=production
   HOST=127.0.0.1
   PORT=3001
   DEV_AUTH=false
   BOT_TOKEN=ВАШ_ТОКЕН_ТОЛЬКО_ЛОКАЛЬНО
   TELEGRAM_PROXY_URL=socks5h://127.0.0.1:ВАШ_ПОРТ
   BOT_ENABLED=true
   APP_URL=
   TUNNEL_PROTOCOL=http2
   TUNNEL_EDGE_IP_VERSION=4
   ```

   `APP_URL` в первый раз может быть пустым: полный launcher заполнит его после проверки туннеля. Не меняйте `DATABASE_PATH`, если там уже ваши поездки. Не используйте `DEV_AUTH=true` для публикации.

5. Запустите `SlopeMate.bat` → пункт **4. Запустить Telegram Mini App** (или сразу `04_TELEGRAM.bat`). Не запускайте параллельно `02_LOCAL`, `03_TUNNEL`, второй `04_TELEGRAM` или ручной `npm start`.
6. Дождитесь сообщения о двух успешных публичных проверках, затем смотрите статусы: HTTP ready, SQLite ready, бот polling, Telegram API ready, меню ready. Состояние `starting` сразу после запуска допустимо: инициализация асинхронная. Launcher периодически выводит обновления.
7. В личном чате с ботом снова отправьте `/start`. Старое сообщение могло содержать предыдущий временный URL; используйте новую кнопку или обновлённое меню.

Во время работы окно launcher должно оставаться открытым. Нужен интернет для Cloudflare, Telegram, WebApp SDK и карт. Локальные `.env` и база не включены в Git; `logs/` тоже исключён.

## Что делает полный launcher

- Проверяет Node 24, npm, `.env`, приватный режим, наличие токена (без вывода), TCP прокси, cloudflared, занятость HTTP-порта и существующие Windows-процессы через CIM/PowerShell.
- Захватывает lock одного launcher для данного checkout. При живом PID второго экземпляра останавливает запуск, а не убивает процесс. Повреждённый lock требует ручной проверки.
- Недоступный TCP-порт прокси даёт предупреждение, но не блокирует приватный HTTP и туннель: Telegram-контроллер отдельно выполнит ограниченные повторы. Неверный формат настроек требует исправления.
- Не захватывает чужой HTTP-сервер на занятом порту: просит закрыть прежний запуск в его исходном окне.
- Запускает собственный production HTTP с проверкой Telegram initData, но временно **без polling** (`BOT_ENABLED=false`). Для верификации подписи токен уже доступен серверу.
- Запускает собственный cloudflared с `--protocol http2 --edge-ip-version 4 --url http://127.0.0.1:3001`. Протокол/семейство IP берёт из `.env`. Выделяет отдельный случайный loopback metrics-порт.
- Убирает HTTP_PROXY/HTTPS_PROXY/ALL_PROXY только из окружения **cloudflared**, не из системы. Это не обходит TUN, firewall или маршруты ОС. Проверка TLS включена.
- Запоминает PID и URL именно этого cloudflared, ждёт регистрации, затем требует два успешных внешних `/api/health` с интервалом. Общий лимит ожидания — 90 секунд плюс уже начавшиеся сетевые запросы. Выданный URL и строка Registered по отдельности недостаточны.
- Атомарно обновляет только `APP_URL` в `.env`, сохраняет остальные строки/секреты и удаляет повторяющиеся строки APP_URL. При ошибке записи не продолжает запуск бота с неверным адресом.
- Корректно останавливает **свой** временный HTTP-процесс и запускает его заново с проверенным URL и polling. Одновременных polling-процессов не создаёт. В этот момент возможен короткий перерыв HTTP.
- Ещё раз проверяет локальный/публичный health. Далее проверяет их примерно раз в 10 секунд и выводит статусы компонентов раз в три цикла. Это наблюдение доступности, не гарантия SLA.

`APP_URL` меняется при новом Quick Tunnel. При его обрыве launcher не создаёт бесконечно новые URL. cloudflared может переподключаться к своему прежнему туннелю штатным механизмом. Если восстановление не происходит, остановите launcher и запустите заново вручную; после нового запуска отправьте боту новый `/start`.

| `SlopeMate.bat`      | Русское меню                                                                                                                            |

| `03_TUNNEL.bat`      | Только туннель к уже запущенному серверу со статусом `production-private`; не обновляет APP_URL/бота. Для обычной работы используйте 04 |

| `05_EDIT_ENV.bat`    | Открыть `.env` в Блокноте                                                                                                               |
| `06_TESTS.bat`       | TypeScript, автоматические тесты и сборка; физический Telegram не проверяет                                                             |

Для полного launcher штатный порт — 3001. `PORT` учитывается backend и туннелем; локальный Vite пока проксирует на 3001, поэтому для `02_LOCAL` используйте `PORT=3001`. В стандартном npm/Node Windows launcher не требует PowerShell-скриптов или смены ExecutionPolicy: PowerShell используется только для чтения списка процессов через CIM.

## Статусы и повторы Telegram

`/api/health` отвечает `{"ok":true}`, если отвечает HTTP-сервер, даже при недоступном Telegram.

`/api/status` публичен и содержит только безопасные диагностические поля: режим HTTP, доступность SQLite, bot/api/proxy/setup, число текущих неудач, задержку и безопасный класс/код ошибки. Токена, URL прокси, владельца, координат, профиля и строк SQL там нет. Остальные личные API требуют Telegram initData; production dev-auth по-прежнему запрещена.

- `bot=polling`, `api=ready`: последний Telegram запрос успешен. Это не обещание постоянного соединения и не замена проверке `/start`.
- `proxy=tcp-ready`: локальный порт открыт. Только успешный `api=ready` подтверждает запрос Telegram через выбранный транспорт.
- `setup=failed`: команды/меню не удалось зарегистрировать за ограниченное число попыток. HTTP остаётся работать, polling пробуется независимо. Проверьте сеть и URL, затем выполните явный перезапуск, чтобы обновить меню.
- Сетевые ошибки init/polling: максимум **6 подряд**, задержки 1, 2, 4, 8, 16 секунд, функция задержки ограничена 30 секундами. Успешный Telegram poll сбрасывает счётчик. При Telegram 429 учитывается retry_after до 300 секунд; более долгий запрет требует ручного повторного запуска позже. Настройка меню имеет отдельные 3 попытки.
- 400/401/403/409 считаются требующими вмешательства, а не бесконечного reconnect. 401 — проверьте токен локально; 409 — проверьте другой polling-процесс или существующий webhook. Приложение не удаляет чужой webhook автоматически. Закройте прежний poller либо осознанно отключите прежнюю webhook-интеграцию штатными средствами Bot API.
- После исчерпания попыток бот `failed`, **HTTP и туннель остаются работать**. Исправьте локальный SOCKS/маршрут Karing и перезапустите launcher вручную. Не запускайте второго бота с тем же токеном.

Используется grammY с `client.baseFetchConfig.agent = SocksProxyAgent`. Все API-вызовы контекстов и основного bot.api наследуют один транспорт. Контроллер вызывает публичные `getMe`, `getWebhookInfo`, `getUpdates`, `handleUpdate`: собственный bounded polling выбран потому, что встроенные `bot.init/start` установленной grammY имеют внутренние длительные повторы. Текущий offset сохраняется при reconnect в рамках процесса. После полного перезапуска допускается повтор последнего не подтверждённого Telegram update; команды здесь не создают поездок.

## Почему TUN может мешать Cloudflare

Наблюдавшиеся `198.20.0.26/27`, адаптер Karing TUN и TLS EOF совместимы с вмешательством FakeIP/маршрутизации, **но сами по себе не доказывают точную причину**. Успешный TCP 7844 к одному edge IP не доказывает TLS и стабильность всего туннеля. `http2`/IPv4 — стартовая конфигурация, а не универсальное исправление.

Для сравнения выполните один запуск без глобального TUN, оставив локальный SOCKS для Telegram. Если ошибка исчезла, сравните DNS/маршруты и правила Karing штатными средствами клиента. Не вносите наугад системные маршруты или DNS. При необходимости настройте исключение Cloudflare из TUN в Karing по документации клиента, сохранив проксирование Telegram. Это внешняя настройка пользователя, launcher её не меняет.

## Различаем 1033 и 502

**1033:** Cloudflare не видит доступный коннектор туннеля. Проверьте, жив ли **нужный PID cloudflared**, что говорит его лог про edge, DNS, TLS EOF и переподключения. URL от другого запуска не подходит. Несколько cloudflared могут иметь разные метрики. Launcher записывает свой PID и URL в `logs/tunnel-state.json`; сохранённый файл после остановки — история, не доказательство живого процесса.

**502:** запрос дошёл до Cloudflare, но origin не дал корректный ответ. Сначала проверьте `http://127.0.0.1:3001/api/health` и статус HTTP-процесса. Если он недоступен — исправляйте локальный сервер/порт. Если доступен — сравните адрес origin, PID и журнал именно этого cloudflared. Telegram API больше не закрывает Express, но это не исключает ошибки порта, падение Node, firewall, рестарт или проблему маршрута туннеля.

**TLS/DNS/timeout без HTTP-кода:** это отдельная транспортная ошибка, не следует автоматически называть её 1033/502. Сертификаты не отключайте.

Публичный health можно открыть с телефона на мобильном интернете по `https://ВАШ-URL.trycloudflare.com/api/health`. Ожидается JSON `{"ok":true}`. При этом `/api/sessions` без Telegram initData обязан возвращать 401. Для подтверждения работы Mini App используйте кнопку внутри Telegram; прямой браузер не авторизуется автоматически.

## Диагностика и остановка

Запустите `07_DIAGNOSTICS.bat` из того же каталога. Он покажет версии Node/npm, наличие cloudflared, занятость HTTP-порта, Windows PID, доступность TCP прокси, локальный/публичный health и текущие статусы сервера. Диагностический режим не делает отдельный `getUpdates` и не конфликтует с ботом. Если APP_URL указывает на старый туннель, отчёт честно проверяет старый адрес; сравните с текущим окном launcher.

Все технические логи идут через редактирование секретов в `logs/launcher-ДАТА.log`; вывод cloudflared помечен компонентом и PID. Исключения Telegram выводят тип/код, без исходных message/request/payload, где библиотеки могут содержать токен. Пароли прокси и известные секреты маскируются, параметры token/password в URL также редактируются. До передачи третьим лицам всё равно просмотрите отчёт: сетевые журналы могут содержать инфраструктурные адреса и локальные пути. Сырые журналы других вручную запущенных программ launcher не очищает.

Для штатной остановки в окне launcher введите **q и Enter**, либо нажмите **Ctrl+C**. Backend получает IPC shutdown, прерывает свои Telegram запросы, закрывает HTTP и SQLite. Зависшие собственные дети завершаются после тайм-аута; на Windows используется taskkill только для ещё живого дочернего PID/дерева. Чужие node/cloudflared процессы по имени не завершаются. Закрытие окна крестиком или аварийное завершение Windows не гарантирует graceful cleanup; используйте q. После аварии повторный запуск проверит lock и занятый порт, а не начнёт убивать найденные процессы.

Если lock-файл повреждён или PID был переиспользован, проверьте процессы в Диспетчере задач/исходном окне. Удаляйте `logs/launcher.lock` вручную только убедившись, что прежний launcher завершён. Несколько checkout с одним Bot Token тоже нельзя запускать одновременно: Telegram вернёт 409; блокировка одного каталога не координирует разные компьютеры.

## Что нужно проверить вручную

Эти изменения проверяются в Linux с локальными mock SOCKS/Telegram API и Chromium. Здесь нет вашего Windows 10, Karing, настоящего токена и реального Cloudflare Quick Tunnel. Поэтому необходимо проверить:

1. Все BAT запускаются двойным щелчком из пути с пробелами, кириллица читается в CMD.
2. Реальный SOCKS-порт Karing доступен при выключенном TUN; `api=ready`, `/start`, `/help`, `/stats` отвечают.
3. Quick Tunnel проходит две проверки, открывается с телефона на другой сети; кнопка и меню содержат новый URL.
4. Выключение SOCKS приводит к retry/failed бота, но локальный и публичный health остаются доступны. Восстановление в пределах попыток возвращает polling; после исчерпания нужен явный перезапуск.
5. Разрыв сети cloudflared правильно диагностируется; новый URL без вашего перезапуска не создаётся.
6. Повторный launcher не стартует второй poller; чужие cloudflared остаются работать. Метрики сверяются с конкретным PID.
7. q/Ctrl+C освобождают порт и собственные процессы; `.env` сохранил токен и остальные строки, SQLite — прежние поездки.
8. Старые тесты GPS/GPX/приватности и реальное открытие на iPhone по-прежнему работают.

Официальный источник схемы агента: https://grammy.dev/advanced/proxy . В текущей cloud-среде чтение этой страницы было заблокировано сетевым proxy (403). Совместимость проверена по установленной grammY (Node: node-fetch, baseFetchConfig.agent) и реальным локальным SOCKS5-соединением в автоматическом тесте, а не по настоящему Telegram/Karing.
