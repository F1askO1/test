# SlopeMate на Windows: локальная работа и постоянный сервер

Windows 10 x64 / Node.js 24 поддерживаются. Главное меню — `SlopeMate.bat`. Код, GPS и база не заменяются. В production всегда `DEV_AUTH=false`; внешняя публикация тестового пользователя запрещена.

## Выберите один сценарий

**Рекомендуемый production:** приложение, SQLite, бот и Caddy постоянно работают на VPS. Домен один и тот же. Настройка описана в [DEPLOYMENT_RU.md](DEPLOYMENT_RU.md). После однократного развёртывания Windows вообще не должен оставаться включённым. `04_TELEGRAM.bat` на Windows становится монитором сервера, не запускает второго бота.

**Windows как хост:** нужен уже настроенный постоянный HTTPS endpoint, который направляет трафик на ваш `127.0.0.1:3001`. Например, собственный reverse proxy/SSH-service или прошедший приёмку Named Tunnel. Launcher не покупает сервис, не создаёт DNS и не управляет внешней учётной записью. ПК, интернет, proxy и коннектор должны работать постоянно. Это менее надёжно, чем VPS.

**Тестирование:** Cloudflare Quick Tunnel доступен только при явном `PUBLIC_ENDPOINT_MODE=quick-test`. Он не становится постоянным от выбора HTTP2/IPv4. Бесплатный Pinggy с часовым сроком и ngrok, отклоняющий IP, не используются как production-схема.

## Общая подготовка

1. Обновите проект до принятого PR, сохранив свой `.env` и каталог `data`. Не копируйте `.env.example` поверх существующего `.env`.
2. Запустите `01_INSTALL.bat`: npm ci и build установят в том числе socks-proxy-agent. Для local-режима он также создаёт недостающие DEPLOYMENT_ID и DIAGNOSTICS_TOKEN в .env без вывода значений и без замены существующих. Для remote эти поля не генерируются: используются данные выбранного сервера. Ошибка TS2307 после обновления исходников означает, что зависимости не соответствуют lockfile; не копируйте только dist или отдельные .ts-файлы.
3. Откройте `.env` через `05_EDIT_ENV.bat`. Launcher не выводит токены. Путь с пробелами поддерживается.
4. Используйте `SlopeMate.bat` → пункт 4 либо `04_TELEGRAM.bat`. Не запускайте параллельно ручной npm start и несколько launcher.

## Постоянный VPS: Windows только наблюдает

После серверного развёртывания задайте в Windows `.env`:

```dotenv
RUN_TARGET=remote
PUBLIC_ENDPOINT_MODE=external
APP_URL=https://app.example.com
DEPLOYMENT_ID=идентификатор_из_серверной_конфигурации
```

Замените домен и deployment ID своими постоянными значениями. ID не секрет; BOT_TOKEN и SOCKS-прокси на Windows для этого сценария не нужны. Не копируйте боевой токен с сервера ради мониторинга. Старый Windows-бот должен быть остановлен.

`04_TELEGRAM.bat` проверяет HTTPS, private production mode, SQLite и принадлежность deployment, показывает состояние бота/меню. Он не создаёт туннель, не меняет APP_URL и не запускает локальные процессы приложения. `q` + Enter или Ctrl+C закрывают монитор; сервер продолжает работать. `07_DIAGNOSTICS.bat` в remote-режиме проверяет сервер, а не ищет несуществующий локальный cloudflared.

## Windows как хост с фиксированным endpoint

В `.env` один раз настройте:

```dotenv
RUN_TARGET=local
PUBLIC_ENDPOINT_MODE=external
NODE_ENV=production
HOST=127.0.0.1
PORT=3001
DEV_AUTH=false
BOT_ENABLED=true
BOT_TOKEN=значение_только_в_вашем_локальном_файле
TELEGRAM_PROXY_URL=socks5h://127.0.0.1:3066
APP_URL=https://app.example.com
```

3066 — SOCKS-порт, сообщённый пользователем для текущего Karing. Он не зашит в код. Если настройки клиента изменились, уточните порт/адрес, тип входа (SOCKS5 или mixed с поддержкой SOCKS) и необходимость логина/пароля. Секреты не отправляйте в чат.

Launcher сначала запускает собственный приватный HTTP без polling, проверяет фиксированный публичный адрес и его deployment ID, затем перезапускает **только свой** backend с ботом и тем же адресом. URL не меняется и .env не переписывается каждый час. Если DEPLOYMENT_ID не задан, для локального режима используется постоянная метка рядом с SQLite. Для удалённого монитора её нужно указать явно.

Внешний постоянный коннектор должен быть запущен своим механизмом/службой до проверки HTTPS. Если его ещё нет — не подставляйте истёкший Pinggy URL. Выберите и настройте постоянное размещение по DEPLOYMENT_RU.md. Launcher остановит свой незавершённый запуск при неверном/чужом endpoint, но не убьёт чужой сервер или tunnel.

Непрерывную доступность Windows нельзя гарантировать: выключение/сон ПК, разрыв Ethernet, проблемы провайдера или локального proxy выводят его из цепочки. Один BAT не отменяет эти ограничения.

## Karing без глобального TUN

Оставьте локальный SOCKS Karing работающим и для первого сравнения выключите глобальный TUN. Не закрывайте весь Karing, если он обслуживает `127.0.0.1:3066`. `socks5h` разрешает имя Telegram на стороне proxy; `socks5` — локально. Если нужна авторизация, URL имеет вид `socks5h://LOGIN:PASSWORD@127.0.0.1:PORT`, специальные символы URL-encode. Значение остаётся только в .env.

TCP-open означает лишь наличие слушателя. Успешный curl HEAD подтверждает короткий HTTPS-запрос, но не длительный getUpdates. Launcher и runtime не меняют системный DNS, маршруты или настройки Karing. Причины конкретных внешних ECONNRESET/TLS EOF всё ещё проверяются на вашем компьютере.

### Исправленный timeout

В socks-proxy-agent 10.1.0 параметр timeout также устанавливал idle timer уже подключённому socket. Старые 10000 мс конфликтовали с getUpdates 25 секунд. Это воспроизведено локальным TLS-тестом: прежний агент обрывает корректно ожидающий запрос, исправленный — получает ответ; неверный сертификат по-прежнему отклоняется.

Теперь таймер SOCKS-handshake очищается после подключения, TLS проверяется штатно, а общую длительность DNS/SOCKS/TLS/HTTP ограничивает grammY RPC deadline:

```dotenv
TELEGRAM_CONNECT_TIMEOUT_MS=10000
TELEGRAM_REQUEST_TIMEOUT_SECONDS=45
TELEGRAM_POLL_TIMEOUT_SECONDS=15
```

RPC deadline должен быть минимум на 10 секунд больше polling timeout и больше connect timeout. Неверная конфигурация не запускает бот; HTTP остаётся доступен. Новое соединение создаётся для каждого запроса (keepAlive=false), что исключает повторное использование потенциально сброшенного proxy-соединения. Это не гарантирует отсутствие внешних сбросов, поэтому требуется длительная приёмка.

## Автоматическое восстановление

Временные ECONNRESET, ETIMEDOUT, ECONNREFUSED, DNS/сетевые ошибки и Telegram 5xx повторяются с exponential backoff и jitter. После шести ошибок бот **не останавливается**: переходит в охлаждение примерно 96–144 секунды и продолжает попытки до восстановления или явной остановки. Счётчик виден в защищённой диагностике, успех polling его сбрасывает. Telegram retry_after учитывается; длительное ожидание разбивается на прерываемые интервалы. Настройка меню повторяется после успешного polling, если раньше не удалась.

Ошибки 400/401/403/404/409, сертификата, программирования или локальной блокировки требуют вмешательства и не маскируются бесконечным reconnect. 401 — проверьте токен, 409 — другой poller или webhook. Приложение не удаляет чужой webhook. Блокировка токена действует на одном хосте/учётной записи; на разных компьютерах нужен организационный контроль «один бот». HTTP и SQLite продолжают работать при сбоях бота.

## BAT-файлы

| Файл               | Назначение                                                                    |
| ------------------ | ----------------------------------------------------------------------------- |
| SlopeMate.bat      | Русское меню                                                                  |
| 01_INSTALL.bat     | npm ci и build, существующий .env сохраняется                                 |
| 02_LOCAL.bat       | Только loopback dev-интерфейс/тестовый пользователь, без бота и публикации    |
| 03_TUNNEL.bat      | Ручной временный Cloudflare для теста приватного HTTP, не production          |
| 04_TELEGRAM.bat    | Fixed external endpoint локального хоста либо монитор VPS согласно RUN_TARGET |
| 05_EDIT_ENV.bat    | Блокнот для локальных настроек                                                |
| 06_TESTS.bat       | check, test, build                                                            |
| 07_DIAGNOSTICS.bat | Безопасные read-only проверки, без второго getUpdates                         |

Для явно выбранного quick-test нужен cloudflared в PATH или CLOUDFLARED_PATH, начальные TUNNEL_PROTOCOL=http2 и TUNNEL_EDGE_IP_VERSION=4. Этот режим сохраняет прежние проверки PID, регистрации и двух публичных health, не убивает чужие процессы и не создаёт новые URL по бесконечному циклу. Он меняет APP_URL на временный: не используйте такой .env для постоянного VPS-монитора. Новый origin меняет доступное localStorage; завершайте GPS-записи до смены адреса.

## Диагностика и остановка

`/api/health` — только жив ли HTTP. `/api/status` — безопасная сводка HTTP/SQLite, deployment ID, bot/api/setup/menu и проверки публичного endpoint. `menu=matches` сравнивает Telegram-меню с текущим APP_URL; `publicEndpoint.state=mismatch` означает, что адрес ведёт к другому deployment. Это разные проверки.

Подробный `/api/diagnostics` требует отдельный DIAGNOSTICS_TOKEN в Authorization Bearer; без него 404. Там есть stage, failures, recovery, nextRetryAt, lastSuccessAt, lastPollSuccessAt, lastFailureAt, proxyCheckedAt и безопасный lastError. Не вставляйте токен в URL/аргументы curl. Launcher читает его из .env, если настроен. lastSuccessAt включает короткие API-вызовы; lastPollSuccessAt подтверждает именно завершившийся getUpdates (до первого ответа он null). Токен доступа к диагностике не заменяет Telegram initData и не даёт доступа к GPS.

Логи Windows находятся в `logs/`, исключены из Git. Известные секреты, userinfo URL и локальные пути маскируются; runtime Telegram не сериализует исходное исключение/request/payload. journald на VPS получает структурированные события. Не включайте DEBUG/NODE_DEBUG с HTTP-пакетами рядом с реальными токенами. Сырые журналы других программ этим приложением не очищаются.

- 1033 / HTTP 530 с кодом 1033: нет доступного Cloudflare connector; проверяйте нужный PID, edge/TLS/DNS и старый URL.
- 502: Cloudflare не получил ответ origin; сначала локальный health, затем адрес/порт/PID конкретного tunnel.
- DNS/TLS/timeout без HTTP-кода: отдельная транспортная ошибка, не автоматически 1033/502.
- 401 `/api/me` вне Telegram: ожидаемая авторизация, не неисправность tunnel. Истёкший initData требует переоткрыть приложение через бота; черновик на том же origin сохраняется.
- 500 при ошибке SQLite теперь является серверной ошибкой и не маскируется как отказ авторизации.

В локальном launcher введите q + Enter или Ctrl+C: завершаются только его дочерние процессы, backend закрывает SQLite и отменяет свои Telegram-запросы. Не закрывайте окно крестиком для штатной остановки. Существующий lock/занятый порт не обходятся убийством чужого процесса. В remote-режиме закрывается только монитор, сервер останавливается через systemctl на VPS.

Перед выводом о стабильности выполните [STABILITY_ACCEPTANCE_RU.md](STABILITY_ACCEPTANCE_RU.md): реальные Windows/Karing, циклы восстановления, работа >60 минут и открытие с iPhone. Автотесты Linux этого не заменяют.
