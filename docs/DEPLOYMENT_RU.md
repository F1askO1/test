# Постоянный SlopeMate: один сервер, домен и HTTPS

## Выбранная схема

Постоянный Linux VPS x86_64 (рекомендуется Ubuntu 24.04 LTS), Node.js 24, Caddy, systemd и SQLite на постоянном диске. Frontend и API обслуживает один Node-процесс; Caddy завершает HTTPS и передаёт запросы на `127.0.0.1:3001`. Домен принадлежит пользователю и не меняется каждый час. Бот обращается к Telegram напрямую с VPS, без Windows/Karing. Это устраняет зависимость продукта от сна домашнего ПК, его IP и срока бесплатного туннеля.

Сервер должен действительно иметь доступ к Telegram API, публичным CA и DNS. Проверка конкретного хостинга до оплаты/развёртывания обязательна: доступность из данной cloud-среды не доказывает доступность из выбранного региона/сети. Рекомендуемый исходный размер для личного использования — 1 vCPU, 2 ГБ RAM, SSD от 20 ГБ; это ориентир, не нагрузочный тест. Размер диска и резервных копий зависит от количества GPS-точек.

Нужны: учётная запись VPS-провайдера, аренда постоянно работающего сервера, домен, SSH-доступ и DNS. Расходы — тариф VPS, регистрация/продление домена и, при необходимости, резервные копии/трафик. Здесь нет актуальной коммерческой оферты: цены и условия сервисов не удалось проверить из-за сетевой политики. Никакие платные ресурсы агент не создавал.

Caddy автоматически выпускает/продлевает сертификаты через ACME. Отдельный платный TLS-сервис не подключается. Но сервер, DNS и доступность CA должны сохраняться; обещать абсолютный uptime нельзя.

## Почему не webhook в этой версии

На VPS используется существующая последовательная обработка `getUpdates`, с восстановлением и systemd. Проблемный локальный прокси из основного production-пути убран. Webhook устранит долгий исходящий `getUpdates`, но ответы, команды и меню всё равно требуют исходящего Telegram API. Он также требует проверки секретного webhook header, подтверждения/повторной доставки и хранения дедупликации. Для этого личного приложения прямой серверный polling проще и уже покрыт тестами. Не включайте webhook одновременно с polling: конфигурационный конфликт останавливает бот, HTTP остаётся работать.

## Однократная подготовка VPS

Дальнейшие команды выполняются **на выбранном пользователем сервере**, а не в Windows CMD. Сначала настройте SSH-ключи, обновления ОС и firewall средствами провайдера/ОС. Разрешите входящий SSH для администратора и TCP 80/443 для Caddy; не публикуйте 3001 и SQLite. Не включайте firewall вслепую до проверки доступа SSH. Добавьте DNS A домена на IPv4 сервера; AAAA добавляйте только при реально работающем IPv6.

Установите `git`, `curl`, `xz-utils` и `caddy` из подписанного репозитория Ubuntu:

```bash
sudo apt update
sudo apt install git curl xz-utils caddy
sudo useradd --system --create-home --home-dir /var/lib/slopemate --shell /usr/sbin/nologin slopemate
sudo install -d -o slopemate -g slopemate /opt/slopemate
sudo -u slopemate git clone https://github.com/F1askO1/test.git /opt/slopemate/current
cd /opt/slopemate/current
```

Если репозиторий закрыт, заранее настройте отдельный read-only GitHub deploy key для сервера; не вставляйте токен в URL команды. После принятия PR код должен находиться в main. Для предварительной проверки используйте ветку PR осознанно, не подключая боевой токен параллельно работающему Windows-боту.

Установите Node 24 из официального HTTPS-дистрибутива с проверкой официального SHA256:

```bash
sudo bash deploy/install-node24.sh 24.22.2
export PATH=/opt/node24/bin:$PATH
sudo -u slopemate env PATH="$PATH" npm ci
sudo -u slopemate env PATH="$PATH" npm run check
sudo -u slopemate env PATH="$PATH" npm run build
```

Скрипт рассчитан на Linux x64, не отключает TLS, проверяет checksum и не перезаписывает неизвестный `/opt/node24` или уже существующий каталог версии. Он не запускался агентом на реальном VPS. Если указанная версия недоступна на официальном сайте, выберите опубликованный поддерживаемый релиз 24.x.y и повторите установку — не подменяйте checksum. Корпоративные CA настраиваются штатно; `--insecure` использовать нельзя.

Создайте production-конфигурацию:

```bash
sudo /opt/node24/bin/node deploy/prepare-env.mjs /etc/slopemate/slopemate.env
sudo nano /etc/slopemate/slopemate.env
```

Генератор создаёт файл только при отсутствии, с правами 0600. Он генерирует DEPLOYMENT_ID и DIAGNOSTICS_TOKEN локально и **не печатает их**. В редакторе задайте BOT_TOKEN и постоянный `APP_URL=https://ваш-домен`. Оставьте `TELEGRAM_PROXY_URL=` пустым, если VPS открывает Telegram напрямую. Секреты не вводите в аргументы команд, Git, чат или историю shell.

Проверьте прямой HTTPS к Telegram **без токена в URL**:

```bash
curl --connect-timeout 10 --max-time 20 -I https://api.telegram.org
```

Ответ на этот короткий запрос не заменяет проверку polling, но выявляет базовую недоступность. Если Telegram с VPS блокируется, смените схему/провайдера до приёмки или настройте доступный SOCKS; webhook сам по себе проблему исходящих ответов не решит.

## Перенос существующей SQLite без потери данных

1. На Windows штатно остановите старый launcher/бот. Убедитесь, что Node больше не пишет в SQLite. Не допускайте одновременно работающих poller с одним токеном.
2. Сделайте резервную копию каталога `data` целиком, включая SQLite и имеющиеся `-wal`/`-shm`. Копирование базы во время записи без SQLite Backup API запрещено этой инструкцией.
3. По защищённому SSH/SFTP перенесите файлы в `/var/lib/slopemate/`. Имя базы должно соответствовать `DATABASE_PATH=/var/lib/slopemate/slopemate.sqlite`. Не заменяйте существующую серверную базу без отдельной резервной копии и проверки, что это нужные данные.
4. Установите владельца `slopemate:slopemate` и закрытые права на каталог/файлы. При переносе только одной базы после подтверждённого checkpoint убедитесь, что не потеряли WAL. При сомнении переносите весь остановленный комплект.
5. Не удаляйте исходную Windows-копию до проверки истории на сервере. Шаблоны deployment не создают другую схему и не очищают существующие таблицы.

Незавершённый GPS-черновик хранится **в WebView конкретного HTTPS origin**, не в SQLite. До смены адреса завершите и синхронизируйте его на старом адресе. Приложение не может читать localStorage другого домена. Постоянный origin устраняет дальнейшую часовую смену хранилища.

## HTTPS и автозапуск

Скопируйте `deploy/Caddyfile.example` в `/etc/caddy/Caddyfile` и замените `app.example.com` на hostname из APP_URL. Не оставляйте документационный домен. Сохраните чужие сайты Caddy, если этот сервер уже используется: не заменяйте существующую общую конфигурацию вслепую.

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
sudo cp deploy/slopemate.service /etc/systemd/system/slopemate.service
sudo systemctl daemon-reload
sudo systemctl enable --now slopemate
sudo systemctl status slopemate --no-pager
```

systemd запускает одного непривилегированного пользователя, постоянный диск `/var/lib/slopemate`, отдельный runtime lock и перезапускает процесс после аварии. HTTP работает независимо от ошибок бота. BOT_LOCK_DIRECTORY=/run/slopemate одинаков в unit и server.env; при ручной проверке используйте тот же файл конфигурации и пользователя, не другую lock-директорию. Блокировка токена не заменяет правило «один production poller»: на разных компьютерах её не разделить, Telegram 409 остановит конфликтующий клиент.

Первичная проверка:

```bash
curl --max-time 10 http://127.0.0.1:3001/api/health
curl --max-time 20 https://ваш-домен/api/status
sudo /opt/node24/bin/node --env-file=/etc/slopemate/slopemate.env deploy/check.mjs
sudo journalctl -u slopemate -n 50 --no-pager
```

Ожидаются HTTP/SQLite ready, правильный deploymentId, Telegram api ready, menu matches и setup ready. Отсутствие входящих сообщений нормально: long polling может ждать без данных. `/api/me` вне Telegram должен возвращать 401; это не поломка endpoint. Проверьте `/start`, кнопку/меню и реальный iPhone. При ошибке меню runtime повторит настройку после успешного polling; старые сообщения `/start` могут содержать прежнюю ссылку — запросите новое.

`/api/status` содержит безопасную сводку. Подробности восстановления доступны только через `/api/diagnostics` с bearer DIAGNOSTICS_TOKEN; без него endpoint возвращает 404. Не вставляйте этот токен в curl-команду или URL. Windows diagnostic launcher читает его из локального .env, если вы решили разрешить подробную диагностику с этого компьютера; для обычного мониторинга он не нужен.

## Поддержка и обновление

- `/api/health` — только HTTP. `/api/status` отдельно различает DB, бот, меню и проверку публичного адреса. Идентификатор является меткой принадлежности, **не механизмом авторизации**.
- Временные ECONNRESET/ETIMEDOUT/ECONNREFUSED автоматически повторяются с jitter и охлаждением. Неверный токен, webhook, второй poller или ошибка сертификата требуют вмешательства. HTTP остаётся доступен.
- systemd Restart=on-failure восстанавливает аварийно завершившийся Node. Он не исправляет DNS, неоплаченный VPS, истёкший домен, выключенную сеть или заполненный диск. Мониторинг/бэкапы остаются обязанностью владельца.
- Перед обновлением остановите сервис, сделайте резервную копию данных, затем выполните fetch/pull только своей принятой ветки, npm ci/check/build от пользователя slopemate и start. Не сбрасывайте пользовательские изменения и не удаляйте data/.
- Не запускайте npm start вручную параллельно systemd. Для остановки: `sudo systemctl stop slopemate`. Для перезапуска после изменения env: `sudo systemctl restart slopemate`.
- Секретный файл находится вне checkout; runtime не должен писать в код. Логи — journald, а не публичный каталог frontend. Настройте допустимый размер журнала и резервное копирование у провайдера; периодически проверяйте свободное место.

Перед объявлением готовности выполните [длительную приёмку](STABILITY_ACCEPTANCE_RU.md). Подготовленные файлы и локальные тесты не являются доказательством уже выполненного серверного развёртывания.
