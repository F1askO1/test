# Приёмка стабильности: минимум 90 минут

Агент не имеет доступа к физическим Windows/Karing/iPhone, реальному Telegram-токену и выбранному VPS. Эти проверки обязательны после однократного развёртывания. Не считать прохождение mocks или просто истечение времени доказательством uptime.

## До начала

- Постоянный домен, корректный HTTPS без игнорирования сертификата, DNS и `/api/status` с нужным deployment ID.
- Ровно один poller: старый Windows-бот остановлен перед включением VPS. setup ready, menu matches. Локальный HTTP/SQLite готовы.
- Существующие данные скопированы с резервной копией; история и профиль видны тому же Telegram-аккаунту. Второй Telegram-аккаунт не видит чужую историю.
- В production DEV_AUTH=false. `/api/me` без initData возвращает 401. Публичная сводка не содержит токенов/счётчиков; `/api/diagnostics` без отдельного bearer возвращает 404.

## Наблюдение >60 минут

На Windows с актуальными APP_URL и публичным DEPLOYMENT_ID выполните `npm run soak`. Он читает .env, опрашивает HTTPS/identity/status каждые ~30 секунд 90 минут, не вызывает Telegram API и не запускает второго бота. DIAGNOSTICS_TOKEN необязателен, он добавляет в отчёт только выбранные технические поля; токен не записывается. Отчёт — `logs/soak-*.jsonl`. SOAK_MINUTES допускает 65–1440; короткий тест не выдаётся за длительную проверку.

Зафиксируйте начало/конец, outages/recoveries, последний успешный Telegram poll, интервалы недоступности и восстановление. Завершённый таймер без истории наблюдений не является успешной приёмкой. Этот 90-минутный прогон агент не выполнял.

## Сценарии

1. Оставьте бот без сообщений минимум на несколько poll-интервалов. Он не должен получать клиентский reset ровно через прежние 10 секунд. API может ждать updates, это нормально.
2. На Windows-хосте выключите только локальный SOCKS Karing на 1–2 минуты, затем включите. HTTP должен оставаться готовым, API recovery показывать backoff/cooldown, polling восстановиться самостоятельно. Не меняйте токен/URL.
3. Повторите отключение на срок, достаточный для более шести ошибок (RPC deadline влияет на длительность). Убедитесь, что бот не становится permanently failed и восстанавливается после возвращения proxy. Выполните минимум три цикла. На VPS без SOCKS проверяйте безопасным временным ограничением исходящего соединения по заранее согласованной сетевой процедуре; не меняйте firewall вслепую и не теряйте SSH-доступ.
4. При стабильном адресе перезапустите backend: данные SQLite остаются, меню matches, Mini App повторно открывается. На VPS проверьте systemctl restart и один контролируемый аварийный сбой с восстановлением systemd, сохранив резервную копию базы.
5. Неверный токен и второй poller проверяйте отдельным тестовым ботом, не боевым. Ожидается fatal 401/409 и готовый HTTP. После исправления конфигурации нужен явный restart. Не запускайте два production-клиента ради диагностики.
6. С iPhone через мобильную сеть отправьте /start, откройте новую кнопку и меню. Проверьте профиль, демо отдельно от рекордов, GPX, карту и историю. Прямой Safari без Telegram не должен авторизоваться.
7. Запишите короткую прогулку при открытом Mini App. Отключите интернет, приостановите/возобновите и повторите сохранение после восстановления. Не обещается фон при блокировке телефона. Повторная отправка не создаёт второй трек.
8. Дождитесь истечения Telegram initData (>1 часа). Получение 401 должно объяснять необходимость переоткрытия, а не говорить «нет связи». Приостановите запись, переоткройте через бота на том же origin и отправьте восстановленный черновик.
9. Перезапустите только Windows-монитор RUN_TARGET=remote: VPS продолжает работать, второй bot/backend не создаётся. URL не меняется ни через час, ни при закрытии Windows.
10. Проверьте неверный/устаревший APP_URL на отдельном тестовом deployment: identity mismatch отличается от недоступной сети и от menu mismatch. Не меняйте DNS боевого приложения ради теста.

Успех: документированные ожидаемые сбои восстановились автоматически, неожиданные простои расследованы, постоянный endpoint сохранился, данные/приватность проверены, iPhone-сценарий выполнен. Если остаются resets вне воспроизведённого клиентского таймера, сохраняйте безопасные времена/stage/error-code и проверяйте Karing/канал отдельно. Увеличение тайм-аута или смена tunnel не являются доказательством исправления внешнего сбоя.
